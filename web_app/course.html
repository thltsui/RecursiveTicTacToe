Stateless REST API

Why we avoid sessions and keep the server purely functional
▶

The Stateless Design Pattern

When building a web game against an AI, it's tempting to store the game state in server memory or a database. However, this introduces complexity: session management, timeouts, and state synchronization issues.

Instead, our Flask backend is entirely stateless. The entire game state is serialized into a JSON object and sent to the client. The client holds the truth of the state, and simply sends it back to the server when it needs an AI move.

Stateless Request Flow Client Server │ │ │ POST /api/move │ │ { "state": {...}, "move": 36 } ────> │ │ │ 1. Deserialize state │ │ 2. Apply move 36 │ │ 3. Run MCTS to get AI move │ │ 4. Apply AI move │ JSON response │ 5. Serialize new state │ <──── { "cells": [...], ... } │ │ │ v v
Benefits of Statelessness
  • Simplicity: No databases or Redis needed.
  • Resilience: The server can be restarted without breaking active games.
  • Scalability: Any server can handle any request.

MCTS Integration

Bridging the gap between a long-running search and a fast web request
▶

Synchronous vs Asynchronous Search

Our MCTS (Monte Carlo Tree Search) takes a few seconds to run, depending on the difficulty (simulation count). We use a simple synchronous request model.

app.pyPython
def do_ai_move(state):
    """Run MCTS and apply AI's move."""
    root = search_mod.run_mcts(
        state, network,
        num_simulations=current_sims,
        dirichlet_epsilon=0.0,  # No noise for gameplay
        device='cpu',
    )
    ai_move = search_mod.select_move(root, temperature=0.0)  # Greedy
    ...

Extracting Analysis Data

MCTS doesn't just output a move; it builds a rich tree of possibilities. We extract the root node's statistics to power the UI's Analysis panel.

  • Win Evaluation: Read directly from the network's value head.
  • Top Moves: Sorted by MCTS visit counts to show what the AI considered.
CPU vs GPU
During training, we use massive batch sizes on the GPU. For the web server, batch size is 1. We force the network to run on cpu because the overhead of moving a single state to GPU memory and back is actually slower than just running it on CPU.

Glassmorphism UI

Designing a premium, modern aesthetic without heavy frameworks
▶

What is Glassmorphism?

Glassmorphism is a UI trend characterized by translucent, frosted-glass effects. It creates depth and visual hierarchy.

Key ingredients:

  1. Semi-transparent backgrounds (using rgba)
  2. Subtle borders
  3. Background blur (using backdrop-filter)
style.cssCSS
.analysis-panel {
    background: rgba(30, 34, 45, 0.4);
    backdrop-filter: blur(12px);
    border: 1px solid rgba(255, 255, 255, 0.05);
    border-radius: 16px;
    box-shadow: 0 8px 32px rgba(0, 0, 0, 0.3);
}

Dynamic Neon Accents

We use bright, neon colors to indicate game state, specifically for the active sub-board ring. This provides critical gameplay information while looking great.

Active Board Highlighting .sub-board.active - Used when the player has "free choice" (all open boards) - Subtle glow: box-shadow: 0 0 12px rgba(cyan, 0.25) .sub-board.active-single - Used when forced into a specific sub-board - Strong pulsing ring: animation: board-pulse-strong 1.8s
04

Optimistic Updates

Keeping the UI responsive despite slow network requests
▶

The Problem

When a user clicks a cell, the server takes up to 10 seconds to respond with the AI's move. If the UI waits for the server response before updating, the game feels broken and laggy.

The Solution: Optimistic UI

We immediately update the local game state and render the player's move on the board before sending the request to the server.

main.jsJavaScript
function onCellClick(sb, cell) {
    // ... validation ...

    // 1. Deep copy the current state to send to server
    const stateToSend = JSON.parse(JSON.stringify(gameState));

    // 2. Optimistically render human move on UI immediately
    gameState.cells[sb][cell] = humanPlayer;
    gameState.legal_moves = []; // prevent double clicks
    renderBoard();

    // 3. Send unmodified state to server
    sendMove(move, stateToSend);
}
Preventing State Corruption
Notice that we deep copy the state before mutating it. If we sent the mutated state, the server would think the cell was already occupied when evaluating the requested move, resulting in an "Illegal Move" error!
