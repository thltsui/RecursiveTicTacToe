01

Game State as a Tensor

Encoding Ultimate TTT for a neural network — 7 channels on a 9x9 grid
▶

What is Ultimate Tic-Tac-Toe?

Ultimate TTT is a 9x9 board made up of nine 3x3 sub-boards arranged in a 3x3 meta-grid. When you play in a cell of a sub-board, you send your opponent to the corresponding sub-board for their next move. Win three sub-boards in a row to win the game.

The 9x9 Board Layout Sub-boards are numbered 0-8: Each sub-board has cells 0-8: 0 | 1 | 2 0 | 1 | 2 --------- --------- 3 | 4 | 5 3 | 4 | 5 --------- --------- 6 | 7 | 8 6 | 7 | 8 A move is a flat index 0-80: move_idx = sub_board * 9 + cell Example: sub_board=4, cell=0 --> move_idx = 36 Mapping to 9x9 spatial grid: row = (sub_board // 3) * 3 + (cell // 3) col = (sub_board % 3) * 3 + (cell % 3)

The GameState Dataclass

The raw game state lives in pure Python — no tensors yet. This separation is deliberate: game logic stays clean and testable, and the neural network gets its own optimized representation.

01_game/board.py Python 
@dataclass
class GameState:
    cells: np.ndarray              # shape (9, 9) -- 0=empty, 1=player1, -1=player2
    sub_board_results: np.ndarray  # shape (9,)   -- 0=ongoing, 1=p1 won, -1=p2 won, 2=draw
    active_sub_board: int          # 0-8, or -1 meaning "free choice"
    current_player: int            # 1 or -1
    move_count: int                # total moves played
    is_terminal: bool
    winner: int | None             # 1, -1, 0 (draw), or None (ongoing)

The 7-Channel Tensor Encoding

Neural networks cannot read Python objects. We convert the game state into a 7-channel, 9x9 tensor — essentially seven 9x9 "images" stacked together, each capturing a different aspect of the position.

Key Insight: Current-Player Perspective
The tensor is always encoded from the current player's point of view. The network always sees itself as "player 1". This means the network only needs to learn one perspective — it halves the problem.
7-Channel Tensor Encoding (shape: 7 x 9 x 9) Channel 0: Current player's pieces 1.0 where I have a piece Channel 1: Opponent's pieces 1.0 where opponent has a piece Channel 2: Active sub-board mask 1.0 for playable cells (all 81 if free choice) Channel 3: Sub-boards I have won 1.0 for all 9 cells of my won sub-boards Channel 4: Sub-boards opponent won 1.0 for all 9 cells of their won sub-boards Channel 5: Drawn sub-boards 1.0 for all 9 cells of drawn sub-boards Channel 6: Turn indicator all 0.0 if I'm player 1, all 1.0 if I'm player -1

Why 7 channels? Each channel answers a yes/no question at every cell. The network learns which combinations of channels matter. For example, "my piece in an active sub-board near my won sub-boards" might be a strong pattern.

01_game/board.py Python 
def encode_state(state: GameState) -> torch.Tensor:
    tensor = torch.zeros(7, 9, 9, dtype=torch.float32)
    cp = state.current_player  # 1 or -1

    for sb in range(9):
        row_block = sb // 3
        col_block = sb % 3
        for cell in range(9):
            row = row_block * 3 + cell // 3
            col = col_block * 3 + cell % 3
            val = state.cells[sb, cell]

            if val == cp:        # Channel 0: my pieces
                tensor[0, row, col] = 1.0
            elif val == -cp:     # Channel 1: opponent's pieces
                tensor[1, row, col] = 1.0

    # Channel 2: active sub-board mask
    if state.active_sub_board == -1:
        tensor[2, :, :] = 1.0        # free choice -- all cells active
    else:
        # only the forced sub-board is active
        sb = state.active_sub_board
        ... # fill only those 9 cells

    # Channel 6: turn indicator
    if cp == -1:
        tensor[6, :, :] = 1.0

    return tensor  # shape: (7, 9, 9)

Move Encoding / Decoding

Moves are flat integers 0–80. This is the format the neural network outputs (a probability for each of 81 possible moves).

01_game/board.pyPython
def decode_move(move_idx: int) -> tuple[int, int]:
    return move_idx // 9, move_idx % 9      # (sub_board_idx, cell_idx)

def encode_move(sub_board_idx: int, cell_idx: int) -> int:
    return sub_board_idx * 9 + cell_idx        # flat index 0-80

Game Rules & Legal Moves

Win detection, the directed-move mechanic, and immutable state transitions
▶

Win Detection

Both sub-boards and the meta-board are 3x3 grids. Winning means getting three in a row along any of the 8 winning lines: 3 rows, 3 columns, and 2 diagonals.

01_game/rules.pyPython
WIN_LINES = [
    (0, 1, 2), (3, 4, 5), (6, 7, 8),  # rows
    (0, 3, 6), (1, 4, 7), (2, 5, 8),  # columns
    (0, 4, 8), (2, 4, 6),              # diagonals
]

def check_sub_board_winner(cells_flat: np.ndarray) -> int:
    for a, b, c in WIN_LINES:
        if cells_flat[a] != 0 and cells_flat[a] == cells_flat[b] == cells_flat[c]:
            return int(cells_flat[a])  # 1 or -1
    if np.all(cells_flat != 0):
        return 2                    # draw -- board is full
    return 0                        # ongoing

The Directed-Move Mechanic

This is what makes Ultimate TTT strategically deep. When you place a piece in cell_idx of a sub-board, your opponent is forced to play in sub-board number cell_idx on their turn. If that sub-board is already won or drawn, they get free choice.

Why This Matters for AI
Every move does two things: (1) claims a cell, and (2) constrains your opponent's options. The AI must reason about both simultaneously. This is why a simple heuristic search falls short.

Legal Moves

01_game/rules.pyPython
def get_legal_moves(state: GameState) -> list[int]:
    if state.is_terminal:
        return []

    if state.active_sub_board == -1:
        # Free choice -- any empty cell in any non-terminal sub-board
        for sb in range(9):
            if state.sub_board_results[sb] != 0: continue
            for cell in range(9):
                if state.cells[sb, cell] == 0:
                    moves.append(encode_move(sb, cell))
    else:
        # Forced to play in the active sub-board
        sb = state.active_sub_board
        for cell in range(9):
            if state.cells[sb, cell] == 0:
                moves.append(encode_move(sb, cell))
    return moves

Applying a Move

Critically, apply_move never mutates the input state. It returns a brand-new GameState. This is essential for MCTS, which explores many hypothetical futures from the same position.

01_game/rules.pyPython
def apply_move(state: GameState, move_idx: int) -> GameState:
    # 1. Validate the move
    # 2. Place piece:        new_state.cells[sb, cell] = current_player
    # 3. Check sub-board:    did this sub-board just get won/drawn?
    # 4. Check meta-board:   did the whole game just end?
    # 5. Set next active:    next_sb = cell_idx of the move played
    #    If that sub-board is already decided -> free choice (-1)
    # 6. Flip player:        new_state.current_player *= -1
    # 7. Increment counter:  new_state.move_count += 1
    return new_state

Legal Move Mask

The network outputs probabilities for all 81 moves, but most are illegal. We create a binary mask to zero out illegal moves before picking one.

01_game/rules.pyPython
def get_legal_move_mask(state: GameState) -> torch.Tensor:
    """Shape (81,): 1.0 for legal, 0.0 for illegal."""
    mask = torch.zeros(81, dtype=torch.float32)
    for m in get_legal_moves(state):
        mask[m] = 1.0
    return mask

04

The Residual Block

Skip connections and KataGo's global pooling injection
▶

What is a Residual Block?

A residual block is the fundamental building unit of our network. It takes a feature map, processes it through two convolution layers, and then adds the original input back (the "skip connection"). This prevents the "vanishing gradient" problem that makes deep networks hard to train.

Intuition
Without skip connections, a 20-layer network would have to learn the entire transformation from scratch. With them, each layer only needs to learn a small residual adjustment. It is much easier to learn "what to change" than "the complete answer."

KataGo's Global Pooling Injection

Standard convolutions only look at local 3x3 patches. But in Ultimate TTT, sometimes a cell's value depends on the global state (e.g., "how many sub-boards have I won?"). KataGo's innovation: add a global pooling branch that squeezes the entire 9x9 feature map into a single vector, processes it through a small MLP, and broadcasts it back to every spatial position.

Residual Block Architecture Input: (B, C, 9, 9) | +---------------------------------------------+ | | Branch 1 (Local): Branch 2 (Global): Conv(C,C,3x3) --> BN --> ReLU GlobalAvgPool --> (B, C) Conv(C,C,3x3) --> BN Linear(C, C/8) --> ReLU | (B, C, 9, 9) Linear(C/8, C) | | (B, C) | Broadcast to (B, C, 9, 9) | | +------------ ADD all three ------------+ | ReLU | Output: (B, C, 9, 9) <-- same shape, richer features
02_network/residual_block.pyPython
class ResidualBlock(nn.Module):
    def __init__(self, channels, global_channels=None):
        # Branch 1: local convolutions
        self.conv1 = nn.Conv2d(channels, channels, 3, padding=1)
        self.conv2 = nn.Conv2d(channels, channels, 3, padding=1)

        # Branch 2: global pooling (KataGo innovation)
        self.global_mlp = nn.Sequential(
            nn.Linear(channels, channels // 8),  # bottleneck
            nn.ReLU(),
            nn.Linear(channels // 8, channels),
        )

    def forward(self, x):
        identity = x                                # (B, C, 9, 9)
        local  = self.bn2(self.conv2(F.relu(self.bn1(self.conv1(x)))))
        pooled = x.mean(dim=[2, 3])               # (B, C)
        glob   = self.global_mlp(pooled)            # (B, C)
        glob   = glob.unsqueeze(-1).unsqueeze(-1)  # (B, C, 1, 1) broadcasts
        return F.relu(local + glob + identity)      # (B, C, 9, 9)

The Policy Head

Converting features to move probabilities, plus an auxiliary opponent head
▶

What Does the Policy Head Do?

The policy head takes the trunk's spatial features (B, C, 9, 9) and produces a probability distribution over all 81 possible moves. This tells MCTS which moves are worth exploring.

Dual Policy: Main + Opponent

A KataGo improvement: we train two policy heads. The main head predicts the current player's best moves. The auxiliary head predicts what the opponent would play. This forces the network to model both perspectives — a strong regularizer during training.

02_network/policy_head.pyPython
class PolicyHead(nn.Module):
    # Each head: Conv(C,2,1x1) -> BN -> ReLU -> Flatten -> Linear(162, 81)

    def forward(self, x):                    # x: (B, C, 9, 9)
        p = F.relu(self.main_bn(self.main_conv(x)))  # (B, 2, 9, 9)
        p = p.flatten(start_dim=1)                   # (B, 162)
        policy_logits = self.main_fc(p)               # (B, 81)

        o = F.relu(self.opp_bn(self.opp_conv(x)))    # opponent head
        opp_logits = self.opp_fc(o.flatten(1))        # (B, 81)

        return policy_logits, opp_logits          # raw logits!

Legal Move Masking

The network outputs raw scores (logits) for all 81 moves, including illegal ones. Before using these as probabilities, we must mask out illegal moves.

Critical Implementation Detail
Set illegal logits to -infinity, then apply softmax. This is mathematically correct: softmax(-inf) = 0. Do NOT multiply logits by a mask — that causes numerical instability.
02_network/policy_head.pyPython
def apply_legal_mask(logits, legal_mask):
    # Set illegal moves to -inf so softmax gives them 0
    masked = logits.masked_fill(~legal_mask.bool(), float('-inf'))
    return F.softmax(masked, dim=-1)  # probabilities, sums to 1.0
06

The Value Head

Multi-output evaluation: win probability, score margin, and sub-board ownership
▶

Why Multiple Outputs?

AlphaZero's value head predicts just one thing: "who is winning?" (a number from -1 to +1). KataGo showed that adding auxiliary prediction targets gives the network a richer training signal. Every game position teaches the network three things simultaneously:

OutputShapeRangeWhat it predicts
win_value(B, 1)[-1, 1]Probability current player wins (main output for MCTS)
score_margin(B, 1)[-1, 1]Predicted sub-board differential (auxiliary)
ownership(B, 9)[0, 1]Per-sub-board win probability (auxiliary)
Why Auxiliary Targets Matter
With win/loss alone, each training example teaches just 1 bit of information. With ownership, it teaches 9 bits. With score margin, it teaches a continuous signal. The auxiliary targets force the network to understand board control, not just final outcomes.
02_network/value_head.pyPython
class ValueHead(nn.Module):
    def forward(self, x):                         # x: (B, C, 9, 9)
        v = F.relu(self.bn(self.conv(x)))          # (B, 1, 9, 9)
        shared = F.relu(self.fc(v.flatten(1)))     # (B, 64)

        win_value    = torch.tanh(self.win_head(shared))      # (B, 1) in [-1, 1]
        score_margin = torch.tanh(self.score_head(shared))    # (B, 1) in [-1, 1]
        ownership    = torch.sigmoid(self.own_head(shared))   # (B, 9) in [0, 1]
        return win_value, score_margin, ownership

Why tanh? Because win value must be bounded to [-1, +1]. tanh naturally maps any real number to that range. Why sigmoid for ownership? Because each sub-board is independently won or lost — it is a per-element binary probability.

The Full Network

Assembling trunk, policy head, and value head into a single model
▶

Architecture Overview

The full network chains together everything we have built. One forward pass transforms a 7-channel board tensor into move probabilities and position evaluation simultaneously.

Full Network Architecture Input: (B, 7, 9, 9) <-- 7-channel board encoding | Input Conv: Conv(7, 128, 3x3) --> BN --> ReLU | v (B, 128, 9, 9) | Residual Trunk: 8 x ResidualBlock(128) <-- each with global pooling | v (B, 128, 9, 9) <-- shared representation | +-----------------+-----------------+ | | Policy Head Value Head Conv(128,2,1) -> FC(162,81) Conv(128,1,1) -> FC(81,64) | | v +----+----+----+ policy_logits (B, 81) win score own opp_logits (B, 81) (B,1) (B,1) (B,9) Total parameters: ~1.3M (128 channels, 8 blocks) Compared to AlphaZero Chess: ~40M (256 channels, 20 blocks)
02_network/network.pyPython
class UltimateTTTNetwork(nn.Module):
    def __init__(self, channels=128, num_blocks=8):
        self.input_conv = nn.Conv2d(7, channels, 3, padding=1)
        self.trunk = nn.Sequential(
            *[ResidualBlock(channels) for _ in range(num_blocks)]
        )
        self.policy_head = PolicyHead(channels)
        self.value_head  = ValueHead(channels)

    def forward(self, x):                    # (B, 7, 9, 9)
        h = F.relu(self.input_bn(self.input_conv(x)))  # (B, C, 9, 9)
        h = self.trunk(h)                               # (B, C, 9, 9)
        policy, opp_policy = self.policy_head(h)
        value_out = self.value_head(h)
        return NetworkOutput(policy, opp_policy, ...)

MCTS Node & the PUCT Formula

Exploration vs exploitation — how to decide which moves to think about
▶

What is MCTS?

Monte Carlo Tree Search (MCTS) builds a search tree by repeatedly simulating games. Each node represents a board position. The neural network guides the search, and the search makes the network's moves stronger than the network alone.

The MCTS Node

Each node stores statistics about how often each action (move) was explored and what value was observed:

StatisticMeaning
N[a]Visit count — how many times we explored action a
W[a]Total value accumulated from action a
Q[a]Mean value = W[a] / N[a] (how good is this move on average)
P[a]Prior probability from neural network (initial belief)

The PUCT Formula

The core of AlphaZero-style MCTS. It balances exploitation (pick moves that looked good) with exploration (try moves the network thinks are promising but under-explored).

PUCT(s, a) = Q(s, a) + c_puct · P(s, a) · sqrt(N(s)) / (1 + N(s, a))

Q(s, a): average value so far. Favors moves that scored well.
P(s, a): neural network's prior. Starts high for moves the network likes.
sqrt(N(s)) / (1 + N(s, a)): exploration bonus. Large when a move has few visits relative to its siblings. Shrinks as we visit more.

03_mcts/node.pyPython
def puct_score(self, move_idx, c_puct=1.0):
    q_value  = self.Q.get(move_idx, 0.0)
    prior    = self.P.get(move_idx, 0.0)
    n_action = self.N.get(move_idx, 0)
    n_parent = self.visit_count

    exploration = c_puct * prior * math.sqrt(n_parent) / (1 + n_action)
    return q_value + exploration

Backpropagation with Negation

After evaluating a leaf node, the value propagates back up the tree. Critically, the value is negated at each level because players alternate — what is good for me is bad for my opponent.

03_mcts/node.pyPython
def backup(self, value):
    self.visit_count += 1
    if self.parent is not None:
        move = self.move_from_parent
        self.parent.N[move] += 1
        self.parent.W[move] += value
        self.parent.Q[move]  = self.parent.W[move] / self.parent.N[move]
        self.parent.backup(-value)  # negate for opponent's perspective!

Dirichlet Noise at Root

To ensure the AI explores diverse openings during self-play, we add random noise to the root node's prior probabilities:

P_noisy(a) = (1 - epsilon) · P(a) + epsilon · Dir(alpha)

alpha = 0.3 (similar to chess), epsilon = 0.25. This noise is only applied at the root of the tree, and only during self-play (not during arena evaluation).

Temperature-Controlled Move Selection

After all simulations, we choose a move based on visit counts:

pi(a) = N(a)^(1/T) / SUM N(a')^(1/T)

T = 1.0 (early game): sample proportionally — encourages diverse opening play.
T = 0.0 (late game): always pick the most-visited move — play the best move.

03_mcts/search.pyPython
def run_mcts(root_state, network, num_simulations=800, ...):
    root = MCTSNode(state=root_state)

    # Expand root with Dirichlet noise
    probs = network.predict(root_state).policy_logits
    probs = apply_legal_mask(probs, legal_mask)
    probs = (1 - epsilon) * probs + epsilon * dirichlet_noise
    root.expand(probs, legal_moves)

    # Run simulations
    for _ in range(num_simulations):
        node  = _select(root, c_puct)          # Phase 1
        value = _expand_and_evaluate(node, net) # Phase 2+3
        _backup(node, value)                    # Phase 4

    return root  # visit counts encode the search result

Policy Target Pruning

KataGo's insight: MCTS visits are optimized for search, not for training
▶

The Problem

During MCTS, we deliberately add noise and use temperature > 0. This means some moves get visited just for exploration — not because they are good. If we train the network to predict these noisy visit counts as-is, we are training on noise.

The Solution: Prune Low-Visit Moves

  1. Convert visit counts to probabilities: pi(a) = N(a) / sum(N)
  2. Remove moves below a threshold (e.g., moves visited only once out of 800)
  3. Renormalize remaining probabilities to sum to 1.0
03_mcts/policy_target.pyPython
def compute_policy_target(visit_counts, num_legal_moves, pruning_threshold=0.0):
    target = torch.zeros(81)
    total_visits = sum(visit_counts.values())

    for move, count in visit_counts.items():
        prob = count / total_visits
        if prob >= pruning_threshold:  # drop noisy single-visit moves
            target[move] = prob

    return target / target.sum()  # renormalize to sum to 1.0

Forced Playouts

A complementary technique: before running MCTS, force at least k visits to every legal move. This prevents the search from ignoring moves the network is currently blind to.

03_mcts/policy_target.pyPython
def add_forced_playouts(visit_counts, legal_moves, forced_playout_k=2):
    """Ensure every legal move gets at least k visits."""
    for move in legal_moves:
        if visit_counts.get(move, 0) < forced_playout_k:
            visit_counts[move] = forced_playout_k
    return visit_counts

Self-Play Data Generation

The AI plays itself to create training data — no human games needed
▶

The Self-Play Loop

This is the key innovation of AlphaZero: the AI generates its own training data by playing against itself. The current network is used for both sides. Each move produces one training example.

Self-Play: One Complete Game state = initial_state() records = [] while not state.is_terminal: | +-- Run MCTS (800 simulations) using current network | | | +-- Get visit counts from root node | +-- Compute pruned policy target | +-- Record: {state_tensor, policy_target, legal_mask, player} | +-- Select move (temp=1.0 for first 30 moves, then temp=0.0) | +-- state = apply_move(state, chosen_move) | end while After game ends: go back and fill in value/score/ownership targets for every recorded move, using the actual game outcome.

What Data Do We Collect?

FieldShapeWhen SetPurpose
state_tensor(7, 9, 9)During gameNetwork input
policy_target(81,)During gameMCTS visit distribution (pruned)
opp_policy_target(81,)During gameNext move's policy (opponent prediction target)
legal_mask(81,)During gameWhich moves were legal
value_targetscalarAfter game+1 win, -1 loss, -0.5 draw
score_targetscalarAfter gameNormalized sub-board differential
ownership_target(9,)After gameDid current player win each sub-board?
Anti-Draw Value Shaping
In early training, the AI fell into a Nash Equilibrium where it played defensively to force draws. A 0.0 value for a draw wasn't punishing enough. We fixed this by assigning -0.5 for draws, strongly incentivizing the agent to take risks and play for the win.
Temperature Schedule
First 30 moves: temperature = 1.0 (sample proportionally from visit counts). This creates diverse training positions. After move 30: temperature = 0.0 (always pick best move). This ensures games reach natural conclusions.

The Replay Buffer

Stable training with a circular buffer of past experience
▶

Why Not Just Train on the Latest Games?

If we only train on the most recent self-play games, the network quickly overfits to its own current style and "forgets" what it learned earlier. This is called catastrophic forgetting. The replay buffer solves this by mixing recent positions with older ones.

How It Works

The replay buffer is a simple circular (ring) buffer that stores individual move records. When full, the oldest positions are overwritten.

Circular Buffer (capacity = 500,000 positions) [old] [old] [old] [new] [new] [new] [newest] [old] [old] ... ^ write pointer When buffer is full, write pointer wraps around, overwriting the oldest positions first. Sampling: random.sample(buffer, batch_size=256) Each batch is i.i.d. -- a random mix of positions from different games and different iterations.
04_training/replay_buffer.pyPython
class ReplayBuffer:
    def __init__(self, capacity=500_000):
        self._buffer = []
        self._position = 0

    def add_game(self, game_record):
        for move_record in game_record.moves:
            if len(self._buffer) < self.capacity:
                self._buffer.append(move_record)
            else:
                self._buffer[self._position] = move_record  # overwrite oldest
            self._position = (self._position + 1) % self.capacity

    def sample(self, batch_size) -> TrainingBatch:
        samples = random.sample(self._buffer, batch_size)
        return TrainingBatch(
            state_tensors=torch.stack([s.state_tensor for s in samples]),
            policy_targets=torch.stack([s.policy_target for s in samples]),
            ...
        )

The Multi-Task Loss Function

Teaching the network five things at once — and why each one matters
▶

The Complete Loss

The total loss is a weighted sum of five components. Each pushes the network to learn a different aspect of the game:

L_total = L_policy + 1.0 * L_value + 0.5 * L_score + 0.5 * L_ownership + 0.15 * L_opp_policy
ComponentLoss TypeWeightWhat It Teaches
L_policyCross-entropy1.0Match the MCTS search distribution (which moves to play)
L_valueMSE1.0Predict game outcome (who will win)
L_scoreMSE0.5Predict sub-board margin (how much am I winning by)
L_ownershipBinary CE0.5Predict which sub-boards I will win (board control)
L_opp_policyCross-entropy0.15Predict opponent's next move (model opponent's strategy)

Policy Loss: Cross-Entropy

The policy target (from MCTS) is a probability distribution. The network outputs logits. We compute cross-entropy after masking illegal moves:

04_training/loss.pyPython
def policy_loss(logits, targets, legal_masks):
    # Mask illegal moves to -inf, then compute cross-entropy
    masked_logits = logits.masked_fill(~legal_masks.bool(), float('-inf'))
    log_probs = F.log_softmax(masked_logits, dim=-1)
    loss = -(targets * log_probs).sum(dim=-1)  # per-sample CE
    return loss.mean()

Value Loss: MSE

Mean Squared Error because value is continuous in [-1, 1]. At training start, this is around 0.5-1.0 (network is guessing). A well-trained network gets this below 0.2.

The Training Loop

Putting it all together: self-play, gradient descent, and evaluation in a loop
▶

The AlphaZero Training Cycle

Each iteration has three phases: generate data, train on data, and (periodically) evaluate the new network against the old one.

Training Loop: One Iteration (~1-2 minutes) Phase 1: SELF-PLAY (network in eval mode, CPU) | Play 25 games against itself using MCTS | Each game ~40-60 moves --> ~1000-1500 new positions | Add all positions to the replay buffer | Phase 2: TRAIN (network in train mode, GPU/MPS) | Sample 50 random batches (B=128) from replay buffer | For each batch: | output = network(batch.state_tensors) | loss = compute_total_loss(output, batch) | loss.backward() | clip_gradients(max_norm=1.0) | optimizer.step() | Phase 3: EVALUATE (every 10 iterations) | Arena: new network vs. best network, 20 games | If win_rate > 55%: replace best network, save checkpoint | Repeat forever until Ctrl+C

The Training Step

04_training/trainer.pyPython
def train_step(network, optimizer, batch, config, device):
    states = batch.state_tensors.to(device)     # (B, 7, 9, 9)

    output = network(states)                     # forward pass
    breakdown = compute_total_loss(output, batch) # all 5 losses

    optimizer.zero_grad()
    breakdown.total.backward()                   # compute gradients
    torch.nn.utils.clip_grad_norm_(              # safety: prevent explosion
        network.parameters(), config.grad_clip_norm
    )
    optimizer.step()                             # update weights

    return breakdown

Checkpointing

The trainer saves checkpoints after each arena evaluation where the new network is better. Each checkpoint stores the network weights, optimizer state, iteration number, and Elo rating. Training can be resumed from any checkpoint.

The Elo Rating System

Mathematically measuring AI playing strength across training
▶

How Elo Works

Elo is a numerical rating that predicts the probability of one player beating another. A 200-point Elo advantage means you win about 75% of the time.

Expected score: E_A = 1 / (1 + 10^((R_B - R_A) / 400))
Rating update: R_new = R_old + K * (actual - expected)

K-factor (default: 32) controls how fast ratings change. Higher K = more volatile, faster convergence. Lower K = more stable, slower to reflect improvement.

06_evaluation/elo.pyPython
def expected_score(rating_a, rating_b):
    return 1.0 / (1.0 + 10.0 ** ((rating_b - rating_a) / 400.0))

def update_elo(rating, opponent_rating, actual_score, k_factor=32.0):
    expected = expected_score(rating, opponent_rating)
    return rating + k_factor * (actual_score - expected)

Elo Tracker

The EloTracker class maintains Elo ratings for multiple network checkpoints across training. It records a full history of (game_number, elo_rating) tuples for plotting the AI's improvement over time.

What Healthy Elo Progression Looks Like
First 10 iterations: rapid jump from 1000 to ~1200. Then steady gain of ~20-30 points per iteration. If Elo is flat for more than 10 iterations, the AI is stuck and needs investigation.

Arena Evaluation

Head-to-head games as the ground truth for AI improvement
▶

Why Arena, Not Just Loss?

Loss decrease does not always mean the AI plays better. A network could memorize training positions while performing worse on novel states. The arena is the definitive test: pit the new network against the previous best in actual games.

Arena Protocol

  • New network plays against the current best over N games (default: 100)
  • Each network plays as both player 1 and player 2 (alternating) for fairness
  • Temperature = 0 (greedy, no randomness) and no Dirichlet noise (deterministic evaluation)
  • If new network wins > 55% of games, it replaces the best network
06_evaluation/arena.pyPython
def run_arena(network_new, network_old, num_games=100, ...):
    wins, losses, draws = 0, 0, 0

    for game_i in range(num_games):
        if game_i % 2 == 0:
            # New network plays as player 1
            result = play_single_game(network_new, network_old, ...)
        else:
            # New network plays as player 2
            result = play_single_game(network_old, network_new, ...)
        # tally wins/losses/draws...

    return ArenaResult(wins, losses, draws, win_rate)

@property
def new_is_better(self):
    return self.win_rate > 0.55  # AlphaZero's 55% threshold
Why 55%?
A 50% win rate means the networks are equally strong. We need a margin above 50% to be confident the new network is truly better (not just lucky). AlphaZero uses 55% as this threshold — statistically significant with ~100 games.
